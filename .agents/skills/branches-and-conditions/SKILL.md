## 目的

読む人が、分岐を見て、どの仕様に基づく処理かを追える形にする。

## 用語

- 条件: 真偽値を求める式（比較・`x != null`・`"a" in x`・型ガード・`type === "a"` など）
- 分岐: 条件の結果で処理を分ける所（if・三項演算子・switch）

## 条件の作り方

- 条件は、仕様に沿って作る
  - 条件ごとに、どの仕様に基づくかを言える実装にする。言えない条件は、実装の都合（データの持ち方・引数の形・抽象化）で生まれたものなので、その都合の側を直す
- 同じ意味の条件は 1 か所で求め、その結果（真偽値）を使う。
  - 同じ意味の条件を 2 か所以上で使うときは、その条件を求める処理を 1 つの関数に書き、使う所はすべてその関数を呼ぶ
  - 関数には条件の元になる値をそのまま渡し、真偽値は関数の中で求める。
    - 呼び出し側で元になる値から真偽値を作ってから関数に渡すと、条件を求める処理が、呼び出し側と関数の 2 か所に分かれることになる
  - その結果（真偽値）を使って分岐する所は 1 か所である必要は無い
  - 対象は、同じ仕様の条件（例: マッチングを起動するかどうか）を複数の所で書くこと。式が似ていても、別の仕様の条件はまとめない

## 引数・データ構造・callback の決め方

### データ構造が同じものは、種類を値で区別する

- 種類（オーダー・商品など）によって違うのが処理（呼ぶ API など）だけで、データ構造（持つプロパティとその型）が同じ場合は、種類を表す値（`type: "order" | "product"` など）で区別する
  - データ構造で区別する（`{ orderIds } | { productIds }`）と、種類を知るためにデータ構造を調べる条件（`in`・型ガード）が、使う所ごとに要る
  - 種類によってデータ構造が違う（持つプロパティが違う）なら、データ構造で区別するのが正しい
- データ構造を調べる条件や、データ構造から中身を取り出し直すための関数が要るなら、データ構造が同じものをデータ構造で区別している合図

### export する関数は、呼び出し元ごとに要る引数だけを受け取る

- 一部の呼び出し元しか使わない引数を export する関数に持たせると、使わない呼び出し元に `undefined` を渡させ、受け取る側に「有るか無いか」の条件を生む
  - 型が `X | undefined` であること自体は問題ではない。データとして値が無い場合がある引数（未入力の項目など）は、どの呼び出し元にとっても要る引数なので対象外
  - 処理を共通にしたい場合は、`undefined` を許す引数をモジュール内の関数に留め、export する関数は呼び出し元ごとに要る引数だけを受け取る

### callback で渡すのは、呼び出し元が決める振る舞いだけにする

- 呼び出し元で先に決まる値なら、callback ではなく値で渡す
- 呼び出し元に返す値は、戻り値で返せるなら callback にしない
- 呼び出し元によって変わらない処理は、callback で受け取らず、関数の中に書く
  - 避ける例: API を順に呼び出す関数に、呼び出す API の処理を callback で渡させる。どの呼び出し元も同じ処理（種類による呼び分けなど）を渡すので、同じ条件が呼び出し元ごとにできる。関数の中で呼べばよい

## 提案のしかた

- 提案する前に定義側と呼び出し側のコードを書き、条件ごとに次を確かめる
  - どの仕様に基づくか
  - 同じ意味の条件を求めている所が 1 か所か
