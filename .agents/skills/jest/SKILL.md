# ルール

- 「このテストが落ちたとき、このファイルのバグだと言えるか？」を基準とする
  - 依存先のバグでテストが落ちるなら、そのテストは不要
- テストは「入力 → 出力・副作用」の振る舞いを検証する
  - mock ばかりのテストは「テストできているつもり」になりやすいため注意する
- 関数の呼び出し順序や、`throw` による自然な帰結はテストしない
- 既に別のテストで保証されているロジックは再テストしない
- 規約に合わない既存のテストは、前例として扱わない
- 単体テストの対象は、ユニット自身が持つロジック（値の変換・計算・条件による判定）に限る
- 以下は単体テストを書かない
  - 配線（依存を呼び出して結果を返すだけの処理）、ライブラリの薄いラッパー
  - API のインターフェース（認可・リクエスト/レスポンスの受け渡し）
  - 外部サービスとの疎通確認（結合テスト・E2E・実環境で確認する）
  - 定数・設定値、型で保証される内容
- `zod` の `schema` は仕様（必須項目・閾値・変換）の定義としてテストする
  - テスト名には、確認している仕様（画面・CSV で必須の項目、閾値の値）を明記する
    - 例：「CSV で必須の項目だけの場合はエラーにならない」「行数が上限（500 件）を超える場合はエラーになる」
- 期待値は実装から独立して導出する
  - mock の戻り値をそのまま assert する、実装と同じ式で期待値を作る等のトートロジーは書かない
- テストに多数の mock が必要な場合は、ロジックを純粋関数に切り出し、その関数をテストする
- アサーションは結果に向ける
  - 処理の実行結果のレスポンスを主な assert 対象とする
  - 関数が「何を引数で呼ばれたか」ではなく「何が返ったか」を見る
- mock 関数のアサーション
  - toHaveBeenCalled / not.toHaveBeenCalled は分岐がある場合のみ使う
    - 「分岐によって呼ばれる/呼ばれないが変わる」場合にのみ意味がある
    - 分岐のないフローで mock 関数の呼び出し有無をテストしない
  - toHaveBeenCalledWith は副作用の内容確認（DB への書き込み内容等）に使う
    - 呼び出しフローの確認目的には使わない
- モックは到達させたい分岐のセットアップ目的に限定する
  - mockRejectedValueOnce 等は「その条件下でルートがどう振る舞うか」を見るためのもの
  - 何を throw/resolve させるか自体はテストの関心ではない
- jest.mock() を使うファイルは beforeEach で jest.clearAllMocks() を呼ぶ
  - テスト間でモック状態が汚染されないようにする
- describe / it の構成
  - describe はテスト対象の単位（関数名・エンドポイント）
  - it の名前は「〜の場合は〜を返す」形式で振る舞いを記述する
  - it の名前はライブラリの動作ではなく、テスト対象のユニットの仕様（呼び出し元が頼っている振る舞い）として書く
- it の単位
  - 1つの it で1つの振る舞いを検証する（複数の関心事をまとめない）
  - ロジックの分岐ごとに it を設ける（分岐の数 = テストケースの最小数）
