## 原則

- 今の呼び出し元が必要とすることを、最も直接的なコードで満たす。
  - 関数・型・引数・ファイル・分岐などの構造は、今の使い手がいる場合にだけ足す
- 「将来使うかもしれない」「後のタスクで共通化できる」は、自分の判断で構造を足す理由にならない。後のタスクで必要になったら、そのタスクで足す
- 一時的なコード（後のタスクで消すもの）のために、共通化の仕組み（新しい関数・引数）を足さない

## 既存のものを先に使う

- ライブラリ・フレームワークの標準の書き方を先に使う。独自の仕組みは、標準の形で書けない理由を言える場合だけにする
  - 避ける例: zustand で、action から `set` を直接呼ばず、間に内部関数の層を挟む
  - 避ける例: TanStack Query で、1 つの操作（保存と、それに続く処理）を `mutationFn` に入れず、外の callback に分ける
- 同じ処理をする既存の関数があれば、新しく作らずにそれを直す
  - 避ける例: 既存の関数に足りない判定があるのに、それを直さずに、同じ処理と判定を持つ別の関数を足す

## PR・ブランチの分け方

- 分けることで、片方の時点だけのための一時的なコードが増えるなら、分けない
  - 避ける例: 登録と更新で PR を分けたため、先の PR の時点だけのために古い関数を残し、コメントを時点ごとに書き分ける

## 方針を出す前に確かめる

方針を提案する前に、方針で追加・変更する要素（関数・型・引数・ファイル・export・分岐・コメント）を一覧にし、要素ごとに次を方針に書く。書けない要素は方針から外すか、書ける形に直す。

- 今それを使う呼び出し元（「後で使う」は数えない）
- 既存のコードを直すことで済まない理由（同じ処理を 2 つ作っていないか）
- ライブラリの上に書くものなら、当たるライブラリの概念（zustand の state / action、TanStack Query の mutationFn / onSuccess など）。当たらないものは独自の仕組みなので、標準の形に直す
