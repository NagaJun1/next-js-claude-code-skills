## 原則

- 1 つの分岐は、1 つの仕様の違いに対応する
  - 書いた分岐ごとに「どの仕様の違いを表しているか」を言えなければ、その分岐は不要
  - 実装の都合（データの持ち方・引数の形・抽象化）で生まれた分岐は、読む人に無い仕様の違いを探させる
- 同じ仕様の違いでの分岐は 1 か所にする
  - 2 か所以上にあるなら、違いを表す値の持ち方が誤っている
- 提案する前に定義側と呼び出し側のコードを書き、分岐ごとに上の 2 つを確かめる

## 不要な分岐が生まれる形

### 種類の違いを、値ではなく形で表す

- 種類の違いを、値（`type: "a" | "b"`）ではなく、プロパティ名や型の形（`{ aIds } | { bIds }`）で表さない。種類を知るために形を調べる分岐（`in`・型ガード）が、使う所ごとに要る
  - 種類によって持つ項目が違うなら、形で分けるのが正しい。対象は、持つデータは同じで、違いが処理の一部（呼ぶ先など）だけの場合
  - 違いは値で持ち、分岐は違いが効く 1 か所（呼ぶ先を選ぶ所）だけに置く
- 形を調べる分岐や、形から中身を取り出し直すための関数が要るなら、種類を形で表している合図

### export する関数に、一部の呼び出し元しか使わない引数を持たせる

- export する関数に、一部の呼び出し元しか使わない引数を持たせない。使わない呼び出し元に `undefined` を渡させ、受け取る側に「有るか無いか」の分岐を生む
  - 型が `X | undefined` であること自体は問題ではない。データとして値が無い場合がある引数（未入力の項目など）は、どの呼び出し元にとっても要る引数なので対象外
  - 処理を共通にしたい場合は、`undefined` を許す引数をモジュール内の関数に留め、export する関数は呼び出し元ごとに要る引数だけを受け取る

### 呼び出し元が決める振る舞い以外を callback にする

- callback で渡すのは、呼び出し元が決める振る舞い
  - 呼び出し元で先に決まる値なら、callback ではなく値で渡す
  - 呼び出し元に返す値は、戻り値で返せるなら callback にしない
  - 呼び出し元によって変わらない処理は、callback で受け取らず、関数の中に書く
    - 避ける例: API を順に呼び出す関数に、呼び出す API の処理を callback で渡させる。どの呼び出し元も同じ処理（種類による呼び分けなど）を渡すので、同じ分岐が呼び出し元ごとにできる。関数の中で呼べばよい
